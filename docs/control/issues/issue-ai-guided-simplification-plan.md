# 生活管理 App｜AI 引導化繁為簡正式規劃

狀態：施工前正式規劃
日期：2026-08-02

## 1. 唯一目標

保留生活管理 App 既有正式功能與資料角色，不刪除能力、不合併資料契約，新增一層「需求辨識、快速分流、直接承接」的使用者介面，讓第一次使用者能快速建立資料、找到既有資料，並在完成後直接看見後續去向與履歷。

## 2. 不變的正式能力

下列角色持續分離，不因 UI 簡化或 AI 導引而合併：

- Item：生活項目
- MaintenancePlan：保養計畫
- Schedule：時間與週期安排
- Task：待處理事項
- WorkCase：問題案件
- WorkCaseUpdate：案件進度
- MaintenanceRecord：完成紀錄
- History：履歷時間線

AI 僅負責理解、整理、建議與導頁；正式程式仍負責驗證、Runtime、transaction、Repository 與資料保存。

## 3. 使用者可見層級

### 第一層：永遠可見

- 首頁快速輸入入口：拍照／語音／輸入
- 今天與近期需要處理
- 最近使用或最近建立的生活項目
- 最近履歷
- 全域搜尋
- 底部主要導覽

### 第二層：依情境顯示

- 先記住生活項目
- 安排定期保養
- 設定日期提醒
- 記錄正在發生的問題
- 記錄已完成的事情
- 繼續處理既有案件
- 補充項目資料

### 第三層：建立後或需要時顯示

- 完整保養計畫
- 排程細節
- 案件進度與更新
- 完成紀錄細節
- 附件、照片、費用、廠商、保固、位置與其他進階欄位
- 分類管理與自訂分類
- 備份、還原及設定

### 隱藏原則

- 不刪功能，只延後顯示。
- 不在第一分鐘要求理解內部資料名稱。
- 自訂分類不阻擋建立。
- 非當前意圖所需的欄位收合到「稍後補充」。
- 空狀態必須提供直接行動，不只顯示說明。

## 4. AI 需求辨識流程

1. 辨識對象：人、物、設備、行程、責任或事件。
2. 辨識意圖：先記住、安排、發生問題、已完成、查詢或尚不確定。
3. 抽取已明確提供的日期、時間、週期、位置、節次、例外與狀態。
4. 不確定時只問一個會改變資料去向的關鍵問題。
5. 顯示一般語言確認卡。
6. 使用者確認後，呼叫既有正式 Runtime。
7. 成功後直接顯示承接結果與履歷入口。

AI 不得：

- 未經確認直接寫入正式資料。
- 捏造日期、週期、品牌、型號、保固或健康／維修結論。
- 將詢問知識誤判為建立資料。
- 繞過 Runtime／Repository／transaction。
- 提供高風險 DIY 維修指導。

## 5. 首頁規劃

首頁不是聊天室。首頁中央只提供輕量快速入口：

- 問句：現在有什麼需要記住或處理？
- 三入口：拍照／語音／輸入
- 範例提示：冷氣漏水、下週四教課、今天換完輪胎

首頁其餘區塊：

- 今天與近期
- 需要繼續處理
- 最近生活項目
- 最近履歷
- 搜尋既有資料

長對話、完整確認與逐項修改在獨立 AI 整理頁完成，不佔據首頁。

## 6. 新增與分流規劃

主要流程：

輸入需求 → AI 整理 → 必要時追問一題 → 確認卡 → 正式建立 → 成功承接 → 履歷

備援分流僅在 AI 不確定時顯示：

- 先記住一件事
- 安排時間或定期事項
- 記錄問題
- 記錄完成
- 只是查詢

使用者說得越完整，系統問得越少；已提供的資訊不得重複詢問。

## 7. 既有資料快速尋找

全域搜尋必須能以名稱、分類、事件文字與履歷摘要找到資料。

常用入口：

- 最近使用
- 最近建立
- 今天／本週
- 進行中的問題
- 已完成
- 分類篩選
- 履歷時間線

搜尋結果直接顯示下一步，例如「繼續處理漏水問題」「查看上次保養」「新增完成紀錄」，不得只打開靜態詳情頁。

## 8. 生活項目詳情規劃

首屏優先順序：

1. 項目名稱、分類與必要摘要。
2. 現在最可能需要的下一步。
3. 目前進行中的問題或近期安排。
4. 最近履歷。
5. 完整資料與進階功能。

固定快捷行動使用一般語言：

- 安排保養
- 記錄問題
- 記錄已完成
- 記住日期
- 補充資料

既有正式功能保留在各自區塊，但不要求新手先理解資料模型。

## 9. 履歷規劃

討論用名稱暫定為「履歷」。

履歷以使用者可理解的事件呈現：建立、安排、發生問題、更新進度、完成、取消或修改。AI 可以整理摘要與回答查詢，但不得把建議、推測或未確認內容寫成已發生事實。

## 10. 施工拆分

### PR 1：入口與資訊層級收斂

- 調整首頁快速入口與可見區塊。
- 將新增頁由功能目錄改成單一需求入口與備援分流。
- 不接正式 AI、不改 Schema、不改 Runtime。
- 使用可替換的本機假解析介面，只驗證 UI 與導航。

### PR 2：既有資料快速尋找

- 全域搜尋、最近使用、最近建立與進行中資料入口。
- 搜尋結果直接連到正確詳情與下一步。

### PR 3：項目詳情下一步引導

- 重新排序首屏資訊。
- 加入一般語言快捷操作。
- 保留完整進階功能於第二層。

### PR 4：AI 文字影子模式

- 文字輸入送至 AI。
- Structured Output 只產生草稿與信心資訊。
- 不自動寫入資料。
- 記錄準確率、延遲、成本與人工修正。

### PR 5：確認後正式建立

- AI 草稿通過 App 驗證後，使用者確認才呼叫正式 Runtime。
- 每種意圖分別接既有正式資料流程。

### PR 6：語音與拍照

- 文字流程穩定後才加入語音與照片。
- 失敗時保留原始輸入並回到人工分流。

每個 PR 只解決一個問題，不得混做 Schema、資料遷移、依賴升級、品牌識別或全面美術重做。

## 11. 第一個施工 PR 的明確範圍

第一個施工 PR 僅做「入口與資訊層級收斂」：

- 不串接真實 AI。
- 不改資料契約。
- 不刪任何正式功能。
- 不合併 Item、Plan、Schedule、Task、Case、Record、History。
- 不重做所有畫面。
- 不改既有建立 Runtime。
- 只改首頁、新增入口、備援分流與必要導航。

## 12. 驗收標準

- 第一次使用者 5 秒內知道從哪裡開始。
- 使用者不需要理解內部資料名稱。
- 主要需求最多三個畫面完成確認。
- 已提供的資訊不重複詢問。
- 任何既有正式功能仍可到達。
- 30 秒內可找到最近建立的資料。
- 60 秒內可完成一筆簡單建立或安排。
- AI／解析失敗時，使用者資料不消失且可人工完成。
- 小螢幕、鍵盤與 200% 文字可操作。
- Analyze、完整 tests、Android build、iOS build 全部通過。

## 13. 與 PR #273 的關係

PR #273 仍為 Draft，程式與 CI 通過但產品實機驗收顯示流程超過五分鐘、分類與功能入口難以理解。不得直接視為完成。

在開始第一個 UI 施工 PR 前，必須先決定：

- 關閉 PR #273，將可重用的小範圍變更重新帶入新 PR；或
- 重新定義 PR #273 範圍並重構為第一個入口收斂 PR。

不得同時維持兩條相互重疊的 UI 施工線。
