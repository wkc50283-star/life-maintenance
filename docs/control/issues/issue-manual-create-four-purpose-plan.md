# 手動建立四入口｜正式施工規劃

狀態：已完成產品規劃，進入施工前工程映射
適用專案：`wkc50283-star/life-maintenance`
基準 main：`0fd7a53df785880ead03bea01d4d118389c4a806`
建立日期：2026-08-08

## 1. 唯一目的

把現有以系統功能名稱排列的手動建立中心，收斂為一般使用者可直接理解的四個生活目的入口；保留既有正式能力，不刪除功能，不先改資料模型，不讓 Codex 自行決定產品方向。

四個正式入口：

1. 建立要長期管理的內容
2. 安排未來要注意或處理的事情
3. 記錄正在處理的事情
4. 補記已完成的事情

四入口只負責「新增」。修改、補充與處理既有內容，從搜尋、列表、詳細頁、履歷關聯或 AI 查詢結果進入。

## 2. 共通產品規則

- 5 秒內應能理解入口用途。
- 簡單情境目標為 60 秒內完成正式建立。
- 第一次只要求最低成立資料，不強迫一次填完整。
- 資料不足但已達最低成立條件，不等於草稿。
- 建立成功後提供「先記錄／繼續補充」。
- 正式建立與正式補充都必須留下履歷。
- 使用者是否補充、何時補充、補充多少，由使用者決定。
- 缺漏不一律提醒；只有影響功能、安全、期限或權益時才提高提示層級。
- 系統可提供後續思考方向，但不得未經確認自動建立提醒、排程、下一次安排或其他正式資料。
- 鎖定產品邏輯，不鎖死介面表現；未經實機驗證的文案、版面、步驟與互動一律標記為待驗證。

## 3. 入口 1｜建立要長期管理的內容

最低成立資料：

- 名稱

第一段可選：

- 分類；略過時使用正式系統「未分類」。
- 管理週期；可零選、一選或多選。

正式管理週期方向：

- 日
- 週
- 月
- 季
- 半年
- 年
- 自訂週期

選擇管理週期本身不得自動建立提醒、排程或 Task。

後續可補充品牌、型號、購買日期、地點、照片、文件、保固、備註、保養內容等，但第一版不得因未補齊而阻擋建立。

### 3.1 自訂管理週期正式規則

自訂管理週期第一版正式定義為：

> 每 N 天／週／月／季／半年／年

其中：

- `N` 必須為正整數。
- 單位只允許：day／week／month／quarter／halfYear／year。
- 例如：每 3 天、每 2 週、每 4 個月、每 3 季、每 2 個半年、每 2 年。
- 自訂管理週期只代表生活項目的管理週期，不得因設定自訂週期自動建立提醒、Schedule 或 Task。
- 不接受自由文字週期，不把「每 3 季」之類內容塞入 note，不得拿 Schedule 冒充管理週期。

資料設計採雙軌：

1. 既有固定週期繼續保留 `ItemManagementPeriod` enum，不破壞現有 day／week／month／quarter／halfYear／year 契約。
2. 自訂週期另外以結構化的 `intervalValue + intervalUnit` 保存。

同一生活項目：

- 可以有 0 個、1 個或多個固定週期。
- 可以有 0 個、1 個或多個自訂週期。
- 可以同時存在固定週期與自訂週期。

完全等價的重複週期不得重複保存。系統在儲存前以標準化值判斷等價，例如：

- 每 7 天 = 每 1 週
- 每 3 個月 = 每 1 季
- 每 6 個月 = 每 1 個半年
- 每 12 個月 = 每 1 年
- 每 2 季 = 每 1 個半年
- 每 4 季 = 每 1 年
- 每 2 個半年 = 每 1 年

正式保存仍保留使用者原始的 `N + 單位` 表達方式；標準化結果只用於判斷等價與防止重複，不得偷偷改寫使用者選擇的顯示方式。

此能力涉及正式 Model／Schema／Migration／History snapshot／Backup／Restore 的可能擴充，因此在資料契約另行定案並完成最小資料基礎 PR 前，Codex 不得自行實作或以其他欄位替代。

## 4. 入口 2｜安排未來要注意或處理的事情

最低成立資料：

- 要注意或處理的事情

關聯生活項目為選填。

第一版產品方向維持四種時間方式：

- 之後再安排
- 指定日期
- 固定重複
- 達到條件時

目前四個名稱尚可在實機驗證後微調，但四種能力與邏輯不得任意增減。

「之後再安排」同時承接尚未分類、尚未知道日期的快速想法，不新增第五個「隨手記」入口。

## 5. 入口 3｜記錄正在處理的事情

最低成立資料：

- 事情名稱

可後補：類型、關聯生活項目、開始時間、目前狀況、照片、費用、文件、人員、預計完成時間等。

只有使用者實際填寫「目前狀況」時，才建立初始進度；不得製造空白進度。

正式底層對應 WorkCase／事件／工程的方式，必須先依現有程式與正式資料角色完成映射，不得由施工者自行合併資料模型。

## 6. 入口 4｜補記已完成的事情

最低成立資料：

- 完成了什麼
- 實際完成日期

實際完成時間與補登時間必須分開處理。使用者只知道日期時，不得捏造時、分。

可後補：關聯生活項目、既有提醒／排程／事件／工程、執行者、費用、材料、照片、文件、結果、備註、後續追蹤與下一次安排。

補登成功後可提供下一步思考方向，但不得自動重新計算下一次、建立排程或改變既有排程。既有「維持原週期」與「依實際完成重新計算」的區別必須保留，實際連動規則另行定案。

## 7. 不新增主入口的功能

下列功能完整保留，但不得增加到手動建立第一層：

- 分類：在生活項目建立／編輯或設定管理。
- 模板：在相關建立流程或設定管理。
- 保養項目與步驟：附屬於相關生活項目／保養內容，不作為第一層生活目的入口。

## 8. 既有資料修改規則

四入口只負責新增。既有資料的編輯、補充、進度、改期、完成、取消、封存等操作，從原資料本身進入。

建立時可以提示可能重複的資料，但不得自動阻止、合併或替使用者決定。

## 9. 履歷規則

正式建立成功時必須產生對應履歷；後續正式補充、修改、關聯、改期、取消、完成等正式變化亦應有可追溯紀錄。

履歷顯示可以整理成自然摘要，但事實只能來自正式資料，不得由 AI 補寫不存在的內容。

施工前必須確認每一個入口目前已有的 History Projection／Runtime／Repository 能力，以及哪些仍缺少原子一致性。

## 10. 資料不完整與提示

缺漏分三層：

1. 不影響使用：只在詳細頁自然提示，不主動催促。
2. 影響功能：明確說明目前哪個能力無法運作，提供直接補充入口。
3. 涉及安全、期限或權益：可以提高提示層級，但仍不得擅自補資料或建立下一步。

不得採用「只要欄位沒填滿就定期提醒」的通用催促機制。

## 11. 使用說明與常見問題

設定中新增「使用說明與常見問題」方向已批准。

規則：

- 任務導向、短篇、情境式。
- 說明適用情境、最低必要資料、建立後會發生什麼、常見誤解。
- 各功能頁可用「？」直接打開對應章節。
- 不得用說明文件掩蓋不好理解的介面；核心操作仍必須做到不看說明也能完成。

此功能不得與四入口第一個施工 PR 綁在一起，應獨立 PR。

## 12. 施工前必做工程映射

在修改 Flutter UI 前，先逐項確認：

- 四入口各自對應現有哪一種正式資料。
- 現有 Model、Repository、Runtime 與 transaction 能重用多少。
- 哪些現有畫面只是 UI，哪些已有完整正式寫入。
- 哪些入口已有履歷能力，哪些沒有。
- 是否需要 Schema／Migration；若需要，立即停工回報，不得自行修改。
- 現有舊資料相容性。
- 正式資料與履歷是否可同一可靠寫入邊界完成。
- 建立失敗、重複點擊、中途離開、讀回失敗等例外。

## 13. 第一批施工順序

施工順序採最小 PR，不一次重做全部：

1. 控制文件與三方工程權責規範同步。
2. 四入口對現有資料／Runtime／Repository／History 的只讀工程映射。
3. 手動建立首頁改為四個生活目的入口與路由骨架；不得刪除既有功能。
4. 入口 1 接入現有一分鐘生活項目正式建立路徑。
5. 共用建立前摘要、成功承接與「先記錄／繼續補充」依實際需要最小化施工。
6. 入口 2 的四種安排方式分支。
7. 入口 3 正在處理流程。
8. 入口 4 補登完成流程與排程連動規則。
9. 設定中的「使用說明與常見問題」。
10. 實機驗收後再處理缺漏提示、草稿、防重複、履歷呈現與其他共用完善。

實際 PR 數量可依工程映射拆得更小，但不得合併未批准產品決策。

## 14. Codex 絕對禁止事項

- 不得自行新增或刪除功能。
- 不得更改四入口目的與數量。
- 不得把選填改成必填。
- 不得自行改文案、流程、預設值或錯誤處理策略。
- 不得自行合併／拆分資料模型。
- 不得自行修改 Schema、Migration 或舊資料規則。
- 不得自行加入提醒、排程、AI、自動化或推播。
- 不得因「比較乾淨」重構無關程式。
- 不得擴大單一 PR 範圍。
- 不得在規格空白時猜測。

遇到需要產品判斷、資料模型判斷或兩種以上合理做法時，必須停止並回報：發現問題、影響範圍、可選方案、風險、建議方案，等待批准。

## 15. 驗收原則

所有未經真實 App 操作的文案、版面、步驟與互動只標記「待實機驗證」。

至少驗證：

- 第一次使用者能否在 5 秒內知道入口。
- 簡單情境能否在 60 秒內完成。
- 大字體、鍵盤、小螢幕與多國語言擴張空間。
- 建立後是否能立即找到正式資料。
- 履歷是否同步存在且內容誠實。
- 重複點擊是否只建立一次。
- 失敗時不留下半筆正式資料。
- iOS 與 Android 行為一致。
- `flutter analyze`、完整 tests、Android build、iOS build 與 `git diff --check` 通過。

UI 最終完成仍需真機人工驗收。
