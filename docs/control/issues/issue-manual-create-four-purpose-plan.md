# 手動建立四入口｜正式施工規劃

狀態：已完成產品規劃；等待最新 main 的只讀工程映射
適用專案：`wkc50283-star/life-maintenance`
基準 main：`8ebffb99ea877ad76931c5d77aa56dbf7f5e3765`
App version：`0.5.53+54`
Schema：v10
最後同步日期：2026-08-09

## 1. 唯一目的

把手動建立第一層收斂為一般使用者可直接理解的四個生活目的入口；保留既有正式功能與資料角色，不刪除能力，不讓 Codex 自行決定產品方向。

四個正式入口：

1. 建立要長期管理的內容
2. 安排未來要注意或處理的事情
3. 記錄正在處理的事情
4. 補記已完成的事情

四入口只負責「新增」。修改、補充與處理既有內容，從搜尋、列表、詳細頁、履歷關聯或 AI 查詢結果進入。

## 2. 共通產品規則

- 第一次使用目標為 5 秒內理解入口用途。
- 簡單情境目標為 60 秒內完成正式建立。
- 第一次只要求最低成立資料，不強迫一次填完整。
- 達最低成立條件即可正式建立，不因欄位未補齊而自動變成草稿。
- 建立成功後提供「先記錄／繼續補充」；是否補充、何時補充、補充多少由使用者決定。
- 正式建立、補充、修改與狀態變化必須可追溯到履歷。
- 缺漏不一律催促；只有影響功能、安全、期限或權益時才提高提示層級。
- 系統可以提出後續方向，但不得未經確認自動建立提醒、排程、下一次安排或其他正式資料。
- 鎖定產品邏輯，不鎖死介面表現。
- 尚未在真實 App 中操作過的文案、版面、步驟與互動，一律標記為「待實機驗證」。

## 3. 入口 1｜建立要長期管理的內容

最低成立資料：

- 名稱

可選：

- 分類；略過時使用正式系統「未分類」。
- 管理週期；可零選、一選或多選。

管理週期正式能力：日、週、月、季、半年、年、自訂週期。

自訂週期採結構化 `intervalValue + intervalUnit`，單位限 day／week／month／quarter／halfYear／year；N 必須為正整數。固定與自訂週期可以並存，完全等價的週期不得重複保存。正式保存保留使用者原始表示方式。

目前 main 已有 ItemCreationRuntime、自訂管理週期資料基礎與管理週期修改履歷 foundation。管理週期本身不得自動建立 Reminder、Schedule 或 Task。

入口 1 的最終四入口 UI、成功頁與「先記錄／繼續補充」仍需依最新 main 做工程映射與實機驗證，不得因資料基礎已存在就標記 UI 完成。

## 4. 入口 2｜安排未來要注意或處理的事情

最低成立資料：

- 要注意或處理的事情

關聯生活項目為選填。

四種時間方式：

- 之後再安排
- 指定日期
- 固定重複
- 達到條件時

「之後再安排」同時承接尚不知道日期的快速想法，不新增第五個「隨手記」入口。

目前 main 已有 FutureMatter v7～v10 正式資料基礎：建立、修改、完成、補充／更正、有效事實 fold、履歷與 Backup／Restore。這些資料能力不得誤認為入口 2 使用者介面已完成。

## 5. 入口 3｜記錄正在處理的事情

最低成立資料：

- 事情名稱

可後補：類型、關聯生活項目、開始時間、目前狀況、照片、費用、文件、人員、預計完成時間等。

只有使用者實際填寫「目前狀況」時，才建立初始進度；不得製造空白進度。

Repo 已有 WorkCase 等正式資料角色，但入口 3 與既有資料角色的最終映射尚未完成最新 main 稽核。施工前必須先做只讀映射，不得由 Codex 自行合併或改寫資料模型。

## 6. 入口 4｜補記已完成的事情

最低成立資料：

- 完成了什麼
- 實際完成日期

實際完成時間與補登時間必須分開。只知道日期時不得捏造時、分。

可後補：關聯生活項目、既有提醒／排程／事件／工程、執行者、費用、材料、照片、文件、結果、備註、後續追蹤與下一次安排。

Repo 已有 MaintenanceRecord 等正式完成資料能力，FutureMatter 也已有 completion／amendment foundation。但「補登完成」、「關聯既有排程」、「維持原週期」與「依實際完成重新計算」的最終連動規則必須逐項依批准規格施工，不得自動建立下一步。

## 7. 不新增主入口的功能

下列能力完整保留，但不得增加到手動建立第一層：

- 分類
- 模板
- 保養項目與步驟

分類在生活項目建立／編輯或設定管理；模板與保養內容在相關流程中承接，不作為第一層生活目的入口。

## 8. 既有資料修改規則

四入口只負責新增。既有資料的編輯、補充、進度、改期、完成、取消、封存等操作，從原資料本身進入。

建立時可以提示可能重複，但不得自動阻止、合併或替使用者決定。

## 9. 履歷規則

- 正式建立成功必須產生或投影對應履歷。
- 正式補充、修改、關聯、改期、取消、完成等正式變化必須可追溯。
- 履歷可以整理成自然摘要，但事實只能來自正式資料，不得由 AI 補寫不存在的內容。
- 施工前必須確認每個入口目前已有的 History Projection／Runtime／Repository 能力與原子一致性邊界。

## 10. 資料不完整與提示

缺漏分三層：

1. 不影響使用：在詳細頁自然呈現，不主動催促。
2. 影響功能：明確說明目前哪個能力不能運作，提供直接補充入口。
3. 涉及安全、期限或權益：可提高提示層級，但仍不得擅自補資料或建立下一步。

不得採用「欄位沒填滿就定期提醒」的通用催促機制。

## 11. 使用說明與常見問題

設定中加入「使用說明與常見問題」方向已批准；採任務導向、短篇、情境式內容。各功能頁可以用「？」直接打開對應章節。

此功能不得與四入口第一個 UI 施工 PR 綁在一起，應獨立 PR。

## 12. 施工前必做的最新 main 工程映射

在修改 Flutter UI 前，先只讀確認：

- 四入口各自對應現有哪一種正式資料。
- 現有 Model、Repository、Runtime、transaction 與 History 能重用多少。
- 哪些畫面只是 UI，哪些已有完整正式寫入。
- 目前 Schema v10 是否已足夠；若任何入口需要新 Schema／Migration，必須停工回報並另案批准。
- 舊資料相容性。
- 正式資料與履歷能否在可靠寫入邊界完成。
- 建立失敗、重複點擊、中途離開、讀回失敗等例外。

## 13. 後續施工順序

1. 控制文件與三方工程權責規範同步。
2. 四入口對最新 main 的 Model／Runtime／Repository／History 只讀工程映射。
3. 使用者逐項批准映射與最小施工規格。
4. 才能建立四入口首頁／路由骨架。
5. 再依單一事項、最小 PR 分別施工入口 1～4 與共用成功／補充流程。
6. 使用說明與常見問題另開 PR。
7. 所有 UI 都必須經實機驗證後才可標記完成。

不得因 FutureMatter 或其他資料 foundation 已經存在，就跳過產品批准或直接把四入口一次做完。

## 15. 驗收原則

所有未經真實 App 操作的文案、版面、步驟與互動只標記「待實機驗證」。至少驗證：5 秒辨識入口、60 秒簡單建立、大字體、鍵盤、小螢幕、多國語言擴張空間、建立後可找到正式資料、履歷同步、重複點擊不重複建立、失敗不留半筆資料，以及 iOS／Android 一致性。

技術 Gate 至少包含 `flutter analyze`、完整 tests、Android build、iOS build 與 `git diff --check`；但 CI 全綠不代表 UI／UX 已完成。
