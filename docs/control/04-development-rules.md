# 生活管理 App 開發與 Codex 規範

狀態：正式控制文件  
適用對象：人工開發者、ChatGPT、Codex 與其他自動化工具。

## 1. 不得混淆專案

- `life-maintenance` 是生活管理 App。
- PMS 是另一個產品概念，不得把 PMS 憲法、文案或資料角色直接帶入本 repo。
- 需求不明時先判斷專案身分，不得自行融合。

## 2. 最小修改

- 每次只修改完成該任務所需的最少檔案。
- 同一檔案只改已確認有問題的最小區塊。
- 不為了排版、重構或「更乾淨」而順便重寫已驗證程式。
- 不得以一次大 PR 同時修改資料、UI、導航與產品流程。

## 3. 先證明再重構

任何重構提案必須先列出：

- 現況與實際證據
- 為何不合邏輯或不可維護
- 最小修法
- 資料相容影響
- 回復方式
- 測試方式
- 明確不修改範圍

## 4. 禁止假功能

不得出現：

- 看似可點但沒有作用的篩選器
- 看似可修改但只是靜態文字的設定
- 尚未完成卻未標示的按鈕
- 測試資料冒充正式資料
- 只有畫面沒有儲存或狀態邏輯的入口

功能未完成時，應暫時移除或明確標示尚未開放。

## 5. 直接語言

- 功能名稱必須讓一般使用者一眼理解。
- 禁止重新導入「先放著」「需要你記住的事」「承接責任」等 PMS 抽象文案。
- 技術模型名稱不得直接顯示在使用者畫面。
- 使用者畫面不得顯示內部 ID。

## 6. 資料變更規則

- 新欄位必須提供舊資料安全預設。
- enum 必須處理未知值。
- 任何格式變更前必須建立不可變原始備份。
- 資料異常時必須鎖住寫入。
- 不得刪除或覆蓋無法解析的來源資料。
- 正式遷移必須有筆數、關聯與回復驗證。

## 7. UI 與視覺規則

- UI PR 必須附實際手機尺寸截圖或錄影。
- 不得只以模擬器「能顯示」判定完成。
- 首頁須在 3 秒內說明用途與目前狀態。
- 表單不可像資料庫輸入工具。
- 空狀態必須說明下一步。
- 處理中、等待、逾期、完成與史略要有清楚差異。
- 設計系統先在一頁驗證，經批准後才擴散到其他頁。

## 8. 分支規則

允許的分支前綴：

- `audit/`
- `fix/`
- `feature/`
- `data-migration/`
- `ui/`
- `docs/`
- `ci/`

禁止直接在 `main` 開發。

## 9. PR 必填內容

每個 PR 必須說明：

- 修改目的
- 修改內容
- 修改檔案
- 明確不修改範圍
- 資料影響
- UI 影響
- 測試結果
- 回復方案

## 10. CI 門檻

每個 PR 至少必須通過：

- `flutter analyze`
- `flutter test`
- `flutter build web --release`

資料遷移 PR 另需：

- 舊資料樣本測試
- 部分損壞測試
- 遷移中斷測試
- 重複執行測試
- 回復測試

## 11. 合併規則

不得合併的情況：

- CI 失敗或尚未完成
- PR 超出申報範圍
- 無資料相容說明
- 有未處理高風險問題
- UI 沒有畫面證據
- 違反產品憲法
- 把 PMS 重新帶回生活管理 App

重大架構、資料遷移與正式 UI 方向由專案負責人最終批准。

## 12. Codex 特別規則

Codex 不得：

- 自行改變產品定位
- 自行創造抽象產品哲學
- 自行合併重大 PR
- 為省事整份重寫
- 把多種生活事件硬塞成同一 Task
- 用備註欄冒充正式資料模型
- 未備份就改資料格式
- 看到測試通過就假設 UX 正確

Codex 應：

- 先讀 `docs/control/`
- 遵守最小修改
- 列出不修改範圍
- 以測試與實際差異證明結果
- 發現規格衝突時停止並提出問題，不得自行選邊

## 13. 完成定義

程式能編譯不是完成。只有同時通過產品、資料、UX、視覺與技術驗收，才可標記完成。

## 14. GPT／使用者／Codex 三方工程權責規範

### 14.1 正式關係

三方不是平行決策關係：

> 使用者決定，GPT 規劃與把關，Codex 施工與回報。

### 14.2 使用者的專屬決策權

只有使用者可以最終批准：

- App 要解決的問題與產品方向。
- 功能新增、保留、修改、延後或刪除。
- 使用流程、入口邏輯與使用者可見文案。
- 欄位必填／選填規則與預設值。
- 正式資料角色、資料模型意義、Schema、Migration 與舊資料規則。
- 提醒、排程、履歷、AI、自動化與同步的產品行為。
- 是否進入正式施工，以及實機驗收是否通過。

技術實作若會改變上述任一產品事實，必須停工並回到使用者批准。

### 14.3 GPT 的責任

GPT 負責：

- 對照最新 main、正式控制文件與已批准決策。
- 主動指出偏離、不合理、過度複雜或不可行的方向，不得迎合。
- 把需求拆成單一事項、最小 PR 與可驗收規格。
- 寫清楚目的、範圍、不做範圍、操作路徑、資料契約、履歷、例外、測試與驗收。
- 發現產品判斷空白時不得交給 Codex 猜測。
- 稽核 Codex 是否超出範圍、偷改產品行為或漏測。

GPT 可以提出反對與替代方案，但不能把建議冒充成已批准決策。

### 14.4 Codex 只允許執行的工作

Codex 只可以：

- 讀取指定正式文件與程式範圍。
- 依已批准施工規格修改指定程式。
- 重用現有正式 Model、Repository、Runtime、transaction 與元件。
- 新增或更新與本 PR 直接相關的測試。
- 執行 format、analyze、test、build 與差異檢查。
- 回報現有程式與規格衝突、無法完成處或需要額外決策的問題。
- 提供修改檔案、測試結果、風險與未完成事項的事實報告。

Codex 的角色是實作、測試、回報，不是產品經理。

### 14.5 Codex 絕對禁止事項

Codex 不得：

- 自行新增或刪除功能。
- 自行改產品方向、入口目的、使用流程或使用者可見文案。
- 自行把選填改成必填，或創造未批准預設值。
- 自行合併、拆分或改變正式資料模型意義。
- 自行修改 Schema、Migration 或舊資料規則。
- 自行加入提醒、排程、推播、AI、自動化、同步或外部整合。
- 自行決定資料回填、關聯或會改變產品行為的錯誤處理策略。
- 因「比較乾淨」「比較好維護」而重構無關程式。
- 擴大單一 PR 申報範圍。
- 為了讓測試通過而改變已批准產品行為。
- 在沒有正式依據或存在兩種以上會造成不同產品行為的方案時自行選擇。

### 14.6 強制停工條件

遇到以下任一情況，Codex 必須停止相關施工並回報：

- 規格與現有程式或正式文件衝突。
- 需要新增或改變 Schema、Migration、Model、欄位或正式關聯，但未在已批准規格中授權。
- 需要改必填／選填、預設值、文案或使用流程。
- 需要刪除既有功能或擴大檔案／功能範圍。
- 舊資料可能受影響。
- 正式資料與履歷無法維持一致性。
- 測試與批准規格互相矛盾。
- 有兩種以上合理實作且會造成不同產品行為。
- 找不到正式依據，必須進行產品判斷才能繼續。

停工回報至少包含：發現問題、影響範圍、可選方案、各方案風險、建議方案與等待批准。

### 14.7 每個 PR 的強制權限宣告

每份正式施工規格與 PR 必須明示：

> 本 PR 僅允許 Codex 依照已批准規格實作與測試。任何產品方向、功能取捨、流程、文案、資料模型、Schema、預設值、欄位必填性、提醒、排程、AI、自動化、刪除既有功能或範圍擴張，均不得由 Codex 自行決定。遇到未定義事項必須停工回報，不得猜測。

### 14.8 衝突時優先順序

- 使用者已批准的正式決策高於 GPT 的建議。
- GPT 的施工規格必須忠實反映已批准決策。
- Codex 的工程偏好不得凌駕正式規格。
- 正式文件與聊天印象衝突時，先停止施工並核對最新批准內容。
- CI 全綠不等於產品完成；UI／UX 仍需實機人工驗收。
